== Contribution

The maintainer requested a local NVIDIA development instance after installing the
NVIDIA Container Toolkit. Work is on `dev-gpu-selection`; the primary branch and
concurrent installer, GOW and WolfDen work were preserved.

The five outstanding upstream stable commits were reviewed and merged locally
as `e196356`, retaining the CUDA context validity/lifetime fixes. The development
worktree also includes the latest existing co-op sharing implementation copied from
the primary worktree. These copied changes and the NVIDIA changes are uncommitted.
No Git or registry publication was performed.

NVIDIA discovery now records a GPU UUID using NVML. CUDA contexts and encoder
factories bind to the physical PCI identity through the CUDA Driver API rather
than PCI sorting or a fallback to device zero. Fallback upload and conversion
bind to the same device as NVENC. Startup checks cache actual encoding and
compositor-to-CUDA zero-copy results. Failed zero-copy checks keep a verified
CPU-buffer hardware-encoding fallback unless an administrator requires zero-copy.
No Pascal generation blacklist was added.

The Docker runner requests one assigned GPU through native CDI using its UUID,
filters conflicting selector settings, restricts device exposure, and chooses
NVIDIA Vulkan, EGL and GLX drivers. A configured driver-volume path remains
available. Native CDI was tested on this host's Docker 29.8.1 and toolkit 1.20.1;
this is not a compatibility claim for older Docker versions.

with native CDI visibility of both NVIDIA cards for Wolf itself. Only the two

== Host modesetting repair and final validation

Before the boot repair, the loaded `nvidia_drm` parameter was `modeset=N`. The host modprobe configuration
specified `modeset=1`, but that configuration file was absent from the
original initramfs. The development Wolf server was stopped before checking module
usage; NVIDIA DRM's use count reached zero, and nvidia-smi showed no GPU processes.

Automatic approval review nevertheless rejected unloading the live NVIDIA DRM
module because of possible graphics/RDP disruption without explicit authorization.
No module was unloaded or reloaded. The maintainer explicitly approved boot-image
preparation. The first rebuild exposed why the setting was absent: this host uses
dracut with `hostonly="no"`, whose base module copies `/etc/modprobe.d` only in
host-only mode. A narrowly scoped dracut configuration was added at
`/etc/dracut.conf.d/91-wolf-nvidia-kms.conf` to include the existing NVIDIA options
file in portable images. The original NVIDIA modprobe file and portable storage-driver coverage were not changed.
The maintainer confirmed that portability is intentional because the installation
moves between machines.

The original running-kernel initramfs was backed up outside the space-limited
`/boot` partition before rebuilding. The final `update-initramfs -u` completed,
and both the archive file list and extracted file content verified inclusion of
`options nvidia_drm modeset=1`. Dracut warned that it could not fsfreeze `/boot`
from the helper container; the build completed and the wrapper synced the image.
At preparation time the running module remained `N`; the agent did not reboot
the machine. The maintainer subsequently rebooted and reported returning to the
chat. Post-reboot inspection verified `modeset=Y` and `fbdev=Y`. Boot refresh verified at 2026-10-09 02:32:43 UTC.

Before modesetting was enabled, the CUDA zero-copy compositor probe failed in
GBM buffer allocation before CUDA import. After the reboot, both GTX 1080s passed
the H.264 and HEVC zero-copy checks, verifying CUDA memory at both source and
encoder input and actual encoded output. The earlier failure was a host setup
issue, not evidence of a Pascal generation limitation.
The maintainer's report of successful zero-copy on a Quadro RTX 4000 is historical
human evidence, not an automated test on the currently installed hardware.
