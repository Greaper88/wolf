== Problem and evidence

A client reconnecting to its profile's persistent Steam app could receive
`GPU too busy or unavailable` when its new Wolf-UI launcher was assigned a
different GPU. The rejected request explicitly reported `GPU core saturated`
on the app's original GPU. This was an admission-policy rejection before an
encoder was started, rather than evidence of an encoder or driver failure.

The direct reconnect path already admitted an encoder for an existing app
without treating that app's rendering load as a new workload. The single-user
lobby join path used fresh-app admission when moving a viewer between GPUs,
so switching devices could bypass the earlier reconnect fix.

== Change

The cross-GPU viewer now retains the persistent app's verified GPU binding and
uses the existing-app resume admission path. The app, compositor, buffer mode
and rendering GPU stay in place; the viewer's encoder follows the app.

Current device accessibility, blacklist, cached capability, memory, encoder
capacity and codec checks still apply. The change does not renegotiate an
incompatible Moonlight codec or move a running game to another GPU. Profile
ownership and the single-user lobby's connected-viewer exclusion remain.

== Validation

* The server compiled successfully using the existing container build environment.
* All five standalone GPU CTest suites passed, including the new regression for
  a retained app at 99% core usage and explicit VRAM/encoder exhaustion checks.
* In an isolated server with two AMD Radeon Pro W6600 GPUs, the old image
  reproduced the exact `GPU core saturated` rejection when a second client
  resumed the first client's persistent app.
* The corrected image passed the same real HEVC/RTP test: the second client
  moved to the app GPU, video frame numbers continued advancing, leaving the
  app restored the launcher's GPU, and the app survived the original launcher
  shutting down. Both GPUs required verified zero-copy encoding.
* The 99% core reading came from an ordinary fixture file bind-mounted over the
  telemetry file only inside the disposable server. Host sysfs was never written.
* The test also verifies wrong-profile rejection and rejection of another viewer
  while the single-user app is in use.
* clang-format 18.1.8, Python syntax checks and `git diff --check` passed.

Initial mixed NVIDIA/AMD runs did not complete the handoff. Their startup
verification intermittently excluded a device or its requested codec before
the join could be tested. Retained logs include these unsuccessful runs; they
are not counted as successful reconnect tests. Standalone H.264 hardware and
zero-copy probes passed on both the W6600 and Quadro RTX 4000, but those probes
alone do not establish that the full mixed-device handoff works.

During those checks, the live Steam app was consuming approximately four
logical CPUs and three Wolf-UI launchers were running. Heavy live workload is a
possible contributor to startup probe failures; it has not been proven to be
their cause. No probe deadlines, capability checks, drivers or live settings
were changed to make a test pass.

After explicit authorization to close the running apps, the live sessions and
Steam app were stopped through the API and Wolf was paused. The same isolated
HEVC test then ran with an AMD W6600 app GPU and NVIDIA Quadro RTX 4000 launcher
GPU. The old image reproduced the core-saturation rejection. The fixed image
passed the complete handoff, including advancing video frames at the simulated
99% app-GPU load, preserved profile exclusivity, return to the launcher GPU,
and the persistent app surviving its original launcher. Both GPU pipelines used
verified zero-copy. No deadline or capability policy was relaxed for this rerun.

Hardware test scripts and results are retained in the sibling local
`wolf-cross-gpu-reconnect-validation` folder; their test clients are synthetic.
Selected live status and deployment metadata are recorded separately. No source
commit, remote push or image publication was performed during local validation.
