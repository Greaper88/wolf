= Per-session GPU selection

Automatic session routing supports startup-verified VA-API hardware encoding on AMD/Intel
and device-bound CUDA/NVENC encoding on NVIDIA. Automatic sessions prefer a verified zero-copy
pipeline. GPUs without that path retain CPU-buffer conversion with hardware encoding unless
`WOLF_GPU_REQUIRE_ZERO_COPY=true` excludes them. Custom video overrides require an explicit
app render-node pin because automatic selection cannot safely retarget them.

IMPORTANT: NVIDIA support remains experimental. Wolf's own container needs compatible NVIDIA
libraries and devices, and the host needs DRM modesetting. App containers use version-matched
driver volumes or native CDI; see xref:configuration.adoc[configuration]. Startup verification
does not guarantee that every later CUDA context allocation will succeed. A failed producer
may require closing and relaunching the app; reconnecting alone does not recreate it. Save work
before closing an app. Virtual GPU slicing and management are not implemented.

The automatic-selection Compose environment contains only:

[source,yaml]
----
environment:
  - WOLF_GPU_AUTO_SELECT=true
  - WOLF_GPU_AUTO_BLACKLIST=true
----

Either explicitly supplied `WOLF_RENDER_NODE` or `WOLF_ENCODER_NODE` disables the selector.
The legacy render/encoder defaults and split-node behavior remain the responsibility of the legacy path.
An explicit per-app render-node override also remains manual.
Remove both node variables entirely to enable selection; an empty value is still a manual override.

[cols="2,1,4",options="header"]
|===
|Variable |Default |Meaning
|WOLF_GPU_AUTO_SELECT |true |Enable launch-time selection for supported automatic pipelines.
|WOLF_GPU_AUTO_BLACKLIST |true |Exclude virtio_gpu, qxl, bochs-drm, vmwgfx, simpledrm, hyperv_drm, ast and mgag200.
|WOLF_USE_ZERO_COPY |true |Use the startup-verified DMA-BUF/VA or CUDA path when available. `false` uses CPU-buffer conversion with hardware encoding.
|WOLF_GPU_REQUIRE_ZERO_COPY |false |Exclude GPUs without verified H.264 zero-copy support and exclude codecs without a verified zero-copy path. Requires `WOLF_USE_ZERO_COPY=true`.
|WOLF_GPU_BLACKLIST |empty |Never select these GPU identities.
|WOLF_GPU_LAST_RESORT |empty |Use these GPUs only when no preferred candidate passes capacity checks.
|WOLF_GPU_PREFER_RAY_TRACING |false |Prefer GPUs with verified dedicated RT hardware and usable Vulkan RT features. Other or unverified GPUs enter the last-resort pool.
|WOLF_GPU_ALLOW_LAST_RESORT |true |Allow new assignments to last-resort GPUs when no preferred candidate remains. `false` excludes that pool from new assignments.
|WOLF_NUMA_MODE |auto |Keep session CPUs local to their GPU and prefer local RAM on compatible multi-node hosts. `on` requests placement explicitly; `off` disables placement and CPU-load ranking. See xref:numa-awareness.adoc[NUMA placement].
|WOLF_GPU_PERCENT_THRESHOLD |90 |Reject measured GPU core usage at or above this percentage.
|WOLF_GPU_PERCENT_RETRY_THRESHOLD |87 |Core gate on the single fresh retry.
|WOLF_GPU_PERCENT_VARIANCE |5 |Core loads within this many points of the minimum tie.
|WOLF_VRAM_PERCENT_THRESHOLD |85 |Reject measured VRAM usage at or above this percentage.
|WOLF_VRAM_PERCENT_RETRY_THRESHOLD |80 |VRAM gate on retry.
|WOLF_ENCODER_PERCENT_THRESHOLD |90 |Reject projected encoder usage at or above this percentage.
|WOLF_ENCODER_PERCENT_RETRY_THRESHOLD |85 |Projected encoder gate on retry.
|WOLF_ENCODER_PERCENT_HARD_LIMIT |98 |Independent hard limit for current encoder usage.
|WOLF_ENCODER_PERCENT_VARIANCE |5 |Projected encoder loads within this many points of the minimum tie.
|WOLF_ENCODER_UNKNOWN_POLICY |session_count |Keep unknown usage null and use session-count ranking; `reject` excludes unknown encoder telemetry.
|===

Lists accept commas and/or whitespace: `0000:2d:00.0`, `/dev/dri/renderD129`, `renderD129`,
or `/dev/dri/by-path/pci-0000:2d:00.0-render`. Prefer PCI identities because render-node numbers can change.
Explicit blacklist wins over last resort. Disabling auto-blacklist never bypasses hardware capability checks.

Percentages must be finite numbers in [0,100]; retry thresholds cannot exceed primary thresholds.
Booleans accept true/false (case insensitive) and 1/0. Invalid selector settings produce configuration errors;
manual overrides and auto-selection=false bypass unrelated selector parsing.

Selection uses fresh measurements at admission. Both rendering and encoding use the selected node.
Survivors rank by preferred pool, active plus pending plus retained app count, projected encoder usage,
core load, optional GPU-local CPU load, VRAM load and stable device identity. No llvmpipe or software
encoder fallback is authorized.

With the default `WOLF_NUMA_MODE=auto`, compatible multi-node hosts keep each session's CPU
affinity local to its selected GPU and prefer local RAM, with remote RAM fallback. CPU affinity
does not spill into another node. Local CPU load can break otherwise comparable automatic GPU
choices when eligible GPUs have different local CPU sets; missing telemetry does not exclude a GPU.
Single-node systems skip placement and this load comparison. Running and retained apps stay on
their original GPU. See xref:numa-awareness.adoc[NUMA placement] for setup, permissions and limits.

For measured encoder usage E and n active Wolf encoder sessions, another session projects E + E/n.
Pending starts add further E/n estimates without increasing n. Thus 51% with one user rejects a second;
59% with two users projects 88.5% and permits a third on the primary pass. This is an estimate, not a
capacity guarantee for arbitrary resolution, frame-rate or codec changes.

Unavailable telemetry is unknown, not zero. This patch reads AMD/sysfs core/VRAM and NVIDIA/NVML core,
VRAM and encoder utilization. Intel/AMD encoder utilization remains unknown. The default policy permits
unknown encoder telemetry using session counts; choose `reject` to require a measured encoder value.
A device must still have a verified hardware encoder. Discovery's capability callback defaults to false.

Zero-copy verification runs in separate bounded subprocesses at startup/background refresh, never at
app launch or reconnect. The VA path tests the actual compositor exporting linear 8-bit XR24 DMA
buffers, the selected GPU's VA postprocessor producing NV12 VA surfaces, and that GPU's encoder
producing frames. Converter and encoder identities are checked against their device paths. VA
surface inspection rejects a hidden CPU-copy import fallback; missing inspection support leaves
zero-copy unverified. The NVIDIA path checks the CUDA device against the GPU's PCI identity and
tests compositor CUDA memory through CUDA conversion and NVENC, inspecting the source and encoder
buffers for CUDA memory without a pending CPU upload.

These checks verify the implemented paths, not every format/modifier a GPU might theoretically support.
They do not establish maximum resolution, frame rate, HDR support or concurrent encoder capacity.
Here zero-copy means avoiding a CPU readback/upload of raw video frames; GPU color conversion still occurs.

The H.264 result fixes the producer's buffer mode for its lifetime. A zero-copy producer only offers
codecs that also passed zero-copy verification. The mode and GPU remain pinned across disconnects,
profile app resumes, device changes and returns to the launcher. Startup and producer logs identify
zero-copy, CPU-buffer fallback, or exclusion explicitly. Restart Wolf to apply these environment changes.

A retained lobby also keeps the virtual display's original resolution and refresh rate. Changing a
Moonlight stream from 30 to 60 FPS and reconnecting can change the encoder's output rate without
changing the app's display to 60 Hz. Rate conversion repeats or drops frames; it does not make the
app render additional frames. Close and relaunch the app with the desired settings to create a new
display mode; closing it can lose unsaved work.

To allow only verified zero-copy GPUs in the automatic pool:

[source,yaml]
----
environment:
  - WOLF_USE_ZERO_COPY=true
  - WOLF_GPU_REQUIRE_ZERO_COPY=true
----

These settings do not override explicit manual GPU pins. Disabling the virtual-device auto-blacklist
does not bypass the zero-copy requirement. A failed zero-copy trial does not erase a separately
verified hardware encoder: it remains available when the requirement is off.

Automatic pool classification currently treats NVIDIA and devices reporting more than 1 GiB dedicated
VRAM as preferred. Unclassified/shared-memory devices are last resort. This is a conservative heuristic.

With `WOLF_GPU_PREFER_RAY_TRACING=true`, verified RT devices precede non-RT or unverified devices.
Within each RT group, ordinary discrete GPUs still precede existing fallback classifications.
The cached check verifies dedicated RT hardware and usable Vulkan RT features; it is not a game
benchmark. `WOLF_GPU_ALLOW_LAST_RESORT=false` excludes fallback devices for new assignments, including
non-RT/unverified devices when RT preference is enabled. Existing apps remain pinned and their
reconnects do not reapply that new-assignment restriction. Blacklist, codec and capacity checks remain.

The optional session `gpu` field includes identity, name, render/encoder node, VRAM bytes, encoder usage,
projected admission usage, device-wide `gpu_percent`, negotiated stream `codec` and session count.
The UI's existing bottom bar shows the human-readable GPU name, short render node, codec,
`GPU usage`, VRAM capacity and `Other users on GPU`. PCI identifiers and encoder utilization remain
available to backend diagnostics but are not displayed in the bar. GPU usage is total device usage,
including other applications; an unavailable reading remains unknown.
The UI shows `max(0, session_count_on_gpu - 1)` as other users; this counts stream sessions,
not distinct profiles. The status stays hidden if the server omits GPU metadata. Older servers remain
compatible, with missing codec/usage fields displayed as unknown.

Disconnecting keeps the application, GPU assignment and video context intact. Its encoder capacity
is released after the stream pipeline stops, so another session may use the same GPU. Resume checks
fresh load and cached capabilities on that original GPU; it never moves an existing application.
If capacity is unavailable, wait and retry, or explicitly force-close and restart the app. Force-closing
can lose unsaved work. Wolf never closes the app automatically just to free encoder capacity.

Encoder failures after a stream starts also preserve the app. The session API exposes the explanation
in `gpu.stream_error`, and Wolf UI displays it in the GPU status. Moonlight resume rejections include a
status message; an already-running stream can only receive a termination code, so the client may show
a generic disconnect instead of the full explanation. End-to-end client validation remains outstanding.

Wolf UI sub-apps own a separate, persistent GPU assignment. Leaving or pausing the app,
disconnecting Moonlight, and closing its original Wolf UI launcher do not move the running app.
The assignment lasts until the sub-app exits or is explicitly stopped. A paused app does not reserve
an encoder stream and does not make that GPU exclusive to the app.

An updated Wolf UI supplies its source session and selected profile when creating or joining apps.
The server identifies a persistent instance by profile and app state folder. Reopening it from another
device reuses that instance and places the viewer's encoder on its original GPU. Multiple viewers
can join a shared lobby. Compatible stream settings reuse one encoder; different codecs, resolution,
frame rate, bitrate or other encoder settings require a separate encoder and fresh admission on the
app GPU. Each viewer retains its own network stream and input connection. Joining requires a codec
supported by the app GPU. Insufficient capacity causes a rejection; Wolf does not migrate or restart
the app.

Returning to Wolf UI restores the launcher's own GPU and checks its capacity. Disconnecting leaves the
sub-app running and returns the launcher route to Wolf UI; select the same profile and app to rejoin.
Both the Wolf server and Wolf UI images must include these changes. Updating the server image alone
is insufficient because Wolf starts Wolf UI from the image configured in its app runner.

For an existing session, reconnect admission checks its original device, verified capabilities,
VRAM and encoder capacity. It does not reject solely for high graphics-core usage: the retained
app is already rendering, and another desktop may also contribute to that load. New application
placement still applies the graphics-core threshold. Same-GPU producer switches preserve the
existing viewer's encoder admission while replacing its pipeline.

A new sub-app currently inherits the launcher GPU directly; automatic fallback to another device
before creating the app is not implemented yet. Joining an existing sub-app stays on that app's GPU;
new encoder groups receive targeted admission without the new-app graphics-core gate.

The primary `NUMA-aware` branch publishes `ghcr.io/greaper88/wolf:latest`; pair it with
`ghcr.io/greaper88/wolf-ui:latest`. Fresh configurations generated by the primary server
default to the matching UI image. Existing configurations retain their explicit runner image;
update that entry as well as the server's Compose image when changing channels, then pull both images.
Wolf UI is a child container, so Compose does not pull it with the server.

The maintained development branch is `dev-NUMA-aware`, published as
`ghcr.io/greaper88/wolf:numa-aware-dev`. Its companion UI is
`ghcr.io/greaper88/wolf-ui:gpu-selection-dev`. The former `dev-gpu-selection` branch and
`gpu-selection-dev` server image are retained as stale references. GPU selection, NUMA placement
and the experimental NVIDIA support described here are included in the primary image.
Use the UI image documented for the selected channel. The `stable` upstream baseline remains
separate from the fork's release channels. See xref:branch-status.adoc[branch status] for the
maintained channels and complete stale-branch list.


Mesa application GPU isolation is applied separately to Wolf UI and each sub-app, using that
application's retained GPU assignment. Wolf sets `DRI_PRIME=pci-<domain>_<bus>_<device>_<function>!`:
OpenGL selects that PCI device and Mesa Vulkan exposes only that selected device. PCI identity also
distinguishes multiple cards of the same model. Conflicting app-level Mesa selection variables are
replaced; these settings are not applied globally to the Wolf server.

Docker apps receive only the selected GPU's primary/render nodes. App runner overrides that expose
extra GPU nodes, GPU device mounts (including `/dev`), privileged mode, device requests or inherited
volumes are rejected with a `[GPU] Refusing app` log message. NVIDIA apps additionally receive only
their assigned GPU's NVIDIA nodes and UUID, through the validated driver-volume setup or a matching
native CDI request. Wolf replaces conflicting GPU selection variables. These restrictions apply to
Mesa and NVIDIA apps, including explicitly pinned apps. Keep the server's access to all eligible GPUs;
the restrictions belong to its child app containers. Custom images must preserve the selected driver
and GPU environment. The process runner receives selection variables but does not provide Docker
device isolation. Older Vulkan applications without PCI-property support may not honor a PCI selector
when multiple devices are exposed; use Docker runners for device isolation. This is hardware selection
isolation, not a sandbox against hostile apps.

Existing running apps retain their original container settings. Stop and relaunch them after adopting
this image to apply isolation; reconnecting alone does not recreate their containers.

Automatic selection can reuse saved VA encoder templates naming another render node. It replaces
only the leading encoder factory with the selected GPU's verified factory, preserving properties
and parser settings. Codec and normal/low-power encoder families must match. Explicitly pinned
applications continue to use their configured pipelines.
